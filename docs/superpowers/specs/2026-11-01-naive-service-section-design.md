## 1. Контекст и задача

Продолжение раздела `content/20-python-runtime/` («Python как рантайм сервиса»,
спека `2026-11-01-python-runtime-section-design.md`). Сюжет курса:

> CPU-кэш → память и рантайм Python → **наивный сервис FastAPI + torch** →
> Triton → (бонус) LLM: continuous batching, KV-cache, SGLang.

Раздел 20 показал четыре боли Python-рантайма по отдельности. Этот раздел
собирает настоящий HTTP-сервис и показывает их **все сразу, в цифрах сервиса**:
latency (p50/p99), throughput и goodput при заданной нагрузке. Затем
добавляется пятая боль — модель обрабатывает запросы по одному — и студент
пишет свой dynamic batcher. Финал раздела: всё, что пришлось написать руками,
становится списком того, что будем проверять у Triton.

Подпроекты 2 (платформа сервисов) и 3 (этот раздел) исходного разбиения
объединены: платформа строится ровно под нужды раздела. Контейнер Triton в
этот подпроект не входит.

Железо: CPU-only, как и раньше. Модель подглав 0–1 — `tinymodel` из раздела 20.

**Изменение 2026-11-07 (решение автора, вариант «обе модели»).** Замер
показал, что свёрточная `tinymodel` на CPU упирается в вычисления: батч 64
дешевле батча 1 на элемент всего в ~1,1 раза (1 поток) и не дешевле при
3 потоках. С подглавы 2 сервис переходит на `widemodel` (`_lib/widemodel.py`):
тот же вход 3×64×64, большие линейные слои, ~112 МиБ весов; батч 32 дешевле
батча 1 на элемент в ~4 раза. Кривая подглавы 2 показывает обе модели, текст
объясняет переход: батч выгоден, когда модель упирается в чтение весов.

## 3. Принятые решения и основания

| Решение | Основание |
| --- | --- |
| Новый `kind` харнесса не вводится | Сервис и нагрузка живут внутри обычного Python-харнесса: `series` для экспериментов, `ab` с метрикой для задания. Runner уже умеет всё нужное: группы процессов, лимиты, метрики. |
| Генератор нагрузки — открытый цикл, latency от запланированного момента | Закрытый цикл («отправил — дождался — отправил») занижает latency перегруженного сервиса (coordinated omission). Студент должен видеть, как p99 взлетает при перегрузке. |
| Генератор и сервис в одном контейнере, генератор прибит к 1 логическому CPU | Иначе генератор крадёт CPU у сервиса, и замер врёт. Ограничение прямо названо в тексте. |
| Задание проверяется по goodput относительно стартового кода в том же прогоне | Абсолютные RPS зависят от машины. Goodput при SLO — та метрика, ради которой батчинг существует: «больше запросов, уложившихся в срок». |
| В задании студент пишет только сбор батча | Суть — политика `max_batch_size` / `max_queue_delay`. Очередь, HTTP-обвязка и раздача результатов по futures даны каркасом; обработка ошибок и отмена разбираются в тексте как то, что «Triton делает за вас». |
| Новых зависимостей нет | FastAPI, uvicorn и httpx уже есть в образе runner. Генератор нагрузки — свой, на asyncio + httpx (или сыром asyncio-сокете, если httpx не тянет нужный RPS на одном ядре — решается спайком, §7 п.1). |

## 4. Содержание раздела

Контент на русском, код на английском. Формат подглав как в разделе 20:
вопрос → замер → модель → задание. Сквозные выноски «Боль сервиса №N»
продолжают нумерацию раздела 20: здесь появляется **№5**.

### 0. Крючок: «CPU свободен, а p99 — секунды»

`series`: наивный сервис — `async def predict`, JSON-тело, `model(x)` прямо
в обработчике, один воркер uvicorn. Нагрузка растёт ступенями по RPS. Линии:
p50, p99 и загрузка CPU сервиса. При росте RPS p99 уходит в секунды, а CPU
занят меньше чем наполовину.

> Сервис стоит в очереди, а процессор отдыхает. Где время?

### 1. Все четыре боли в одном сервисе

Одна таблица/график: тот же сервис, по очереди исправляем по одной боли из
раздела 20 и смотрим, сколько миллисекунд p99 и сколько RPS каждая стоила:

- `async def` с синхронной моделью → обычный `def` (боль №3);
- JSON → бинарное тело (боль №4);
- 1 воркер → N воркеров × потоки torch (боль №2), с ценой по памяти (боль №1).

Блоки — `series` с переключаемыми вариантами сервиса (файлы в `snippets/`),
без задания: студент запускает и сравнивает. Ссылки назад на подглавы
раздела 20.

### 2. Потолок: модель зовётся с батчем из одного

`series`: время инференса `tinymodel` на элемент при батче 1, 2, 4 … 64.
Батч 32 обходится на элемент в разы дешевле батча 1 (точное число — замер).
Вывод: исправленный сервис упирается не в Python, а в то, что каждый запрос —
отдельный вызов модели.

→ **Боль сервиса №5: модель обрабатывает запросы по одному.**

### 3. Dynamic batching: идея

Схема: запросы кладутся в очередь, отдельная задача собирает батч — первый
запрос ждём сколько угодно, остальные добираем, пока не набралось
`max_batch_size` или не истёк `max_queue_delay` с момента первого; батч
уходит в модель (в потоке, см. раздел 20 подглава 4); результаты раздаются
по futures. `viz id=batch-queue`: временная шкала прихода запросов, окна
сбора и отправки батчей при разных `max_queue_delay`.

### 4. Задание: собрать батч

Контракт:

```python
async def collect_batch(queue: asyncio.Queue, max_batch_size: int,
                        max_delay: float) -> list
```

Стартовый код возвращает список из одного элемента (`[await queue.get()]`).
Каркас (не редактируется) — FastAPI-приложение с бинарным протоколом,
воркерами и потоками в разумной конфигурации, цикл
«`collect_batch` → модель в потоке → раздача результатов».

Проверка (`kind: ab`): для стартового кода и кода студента поочерёдно
поднимается сервис, подаётся одна и та же открытая нагрузка выше потолка
наивного сервиса, меряется goodput при SLO p99 (значения SLO и RPS — из
калибровки). Метрика `goodput_ratio = goodput(студент) / goodput(старт)`,
цель `goodput_ratio >= X` (X калибруется, ориентир 2). Корректность: каждый
ответ совпадает с эталонным выходом модели для своего входа (бинарное
сравнение с допуском), ни одного ответа, отданного чужому запросу.

Ловушки, которые harness различает и сообщает студенту понятным текстом
(через stderr → блок диагностики):

- батч никогда не отправляется, пока не наберётся `max_batch_size`
  (зависание при малой нагрузке) — отдельный короткий прогон с редкими
  запросами и проверкой latency ≤ `max_delay` + время модели;
- busy-wait в цикле сбора (CPU 100 %, goodput падает).

### 5. Компромисс latency ↔ throughput

`series`: для решения студента (или эталона) — p50, p99 и throughput при
нескольких `max_queue_delay`. Больше ожидание — выше throughput и выше
p50 при малой нагрузке. Нет универсального значения: его выбирают под SLO.

### 6. Вывод и мост к Triton

Таблица: что пришлось сделать руками (воркеры × потоки, бинарный протокол,
очередь, сбор батча, подбор `max_queue_delay`) и чего мы **не** сделали
(ошибка одного запроса в батче, отмена запроса клиентом, backpressure при
переполнении очереди, несколько моделей, метрики). Следующий раздел
проверит замерами, что из этого Triton даёт конфигурацией
(`dynamic_batching`, `instance_group`, `max_queue_delay_microseconds`) и что
по-прежнему настраивается руками. Без утверждений, которые не проверены.

## 5. Платформа

### 5.1. `servicelib.py`

Живёт в `content/30-naive-service/harness/_lib/`, копируется runner'ом рядом
с `bench.py` (механизм `_lib` из раздела 20).

- `start_service(app_path: str, *, workers: int = 1, torch_threads: int | None = None, cpus: set[int]) -> ContextManager[str]`:
  поднимает `uvicorn` подпроцессом на `127.0.0.1:<свободный порт>` с
  приложением из файла (код студента или вариант из `snippets/`), привязывает
  его к `cpus`, ждёт `GET /health`, отдаёт базовый URL; при выходе — SIGTERM,
  затем SIGKILL группе. Падение сервиса при старте → исключение с его stderr.
- `run_load(url: str, *, rps: float, duration_s: float, make_body, cpus: set[int]) -> LoadResult`:
  открытый цикл; запрос *i* планируется на `t0 + i/rps`; latency = момент
  ответа − запланированный момент; ошибки и таймауты считаются отдельно.
- `LoadResult`: массив latency, число ошибок, `p50()`, `p99()`,
  `throughput()`, `goodput(slo_ms)`.
- Разбиение CPU: `split_cpus() -> (load_cpus, service_cpus)` — 1 логический
  CPU генератору, остальные сервису; при < 4 логических CPU — сообщение
  «задание требует ≥ 4 логических CPU» и exit 3 (как в задании 2 раздела 20).

### 5.2. Честность замера

- генератор прибит к своему CPU, сервис — к остальным (`os.sched_setaffinity`
  на процессы uvicorn);
- прогрев сервиса (несколько запросов) вне замера;
- для `ab`: варианты по очереди, каждый со своим поднятием сервиса;
  чередование A/B на уровне повторов, как в разделе 20;
- каждый запуск блока ≤ ~30 с; число ступеней RPS и длительность — из
  калибровки.

### 5.3. Ограничения runner

Лимиты runner не меняются без нужды. Ожидаемые узкие места, проверяемые
калибровкой: `RLIMIT_NPROC` (256), `mem_limit 3g` при нескольких воркерах с
torch, сетевые сокеты на loopback (доступны во внутренней сети compose).

### 5.4. `tinymodel`

Раздел 30 использует ту же модель, что и раздел 20. `_lib` разделов
независимы, поэтому `tinymodel.py` копируется в `30-naive-service/harness/_lib/`
с комментарием об источнике; общий `_lib` уровня `content/` — вне границ
(потребовал бы изменения механизма копирования).

## 7. Открытые вопросы

1. **Решено (спайк, runner, 16 логических CPU, генератор на CPU 0, сервис на 1..15).**
   httpx.AsyncClient (keep-alive) держит расписание до ~800 RPS (lag p99
   ~0.01 мс, 0 ошибок); на 1000 RPS генератор разваливается (lag p99 22 мс,
   latency p99 7.6 с). Сырой asyncio HTTP/1.1 keep-alive держит ≥ 4000 RPS
   (lag p99 < 0.01 мс, latency p99 0.2 мс; на 6000 уже срыв). Решение:
   `run_load` на сыром asyncio keep-alive.
   **Уточнено при реализации `servicelib` (задача 1)**: lag — собственная задержка
   генератора: момент, когда тело готово (`make_body`), минус план; ожидание
   соединения и ответа — latency/ошибки сервиса, не lag (иначе перегруженный
   сервис с переполненной очередью accept выглядел бы как отстающий
   генератор). Потолок ниже мерился с более строгим определением (lag до
   записи в сокет, включая ожидание соединения), так что это нижняя оценка. Против
   тривиального FastAPI-сервиса (1 воркер, POST 1 байт) генератор на одном
   CPU стабильно держит расписание до ~10000 RPS (lag p99 ~0.01 мс, 0 ошибок,
   3 прогона); с 12000 RPS — срыв (lag p99 5-80 мс), единичный срыв был и на
   8000. Цифры спайка (~4000, срыв на 6000) против этого клиента не
   воспроизвелись. Рабочие ступени по-прежнему разумно держать ≤ ~2000 RPS
   (запас ×4 до потолка); защитой служит `LoadGeneratorLagging` (lag p99 > 5 мс).
2. Конкретные RPS, SLO, длительности и порог `goodput_ratio` — калибровка.
   Входные данные спайка: наивный сервис на `tinymodel` (батч 1, sync
   `def`, `torch.set_num_threads(1)`), сырой генератор: латентность p50
   ~3.9 мс, p99 ~5 мс до 1200 RPS без ошибок; на 2000 RPS срыв
   (1 воркер: p99 331 мс; 4 воркера: p50 36 мс, p99 85 мс). Т.е. ёмкость
   одного воркера ~1200-1500 RPS, а 4 воркера на этих загрузках заметно не
   прибавляют (узкое место не в числе воркеров при таком малом запросе).
   Для демонстрации перегрузки нужны ступени около 1200-2000 RPS либо более
   тяжёлая модель/нагрузка на запрос.
3. **Решено.** Пиковая сумма PSS (воркеры uvicorn с torch + tinymodel,
   `--workers N`): 1 -> 257 МиБ, 2 -> 463, 4 -> 802, 8 -> 1474 МиБ
   (~185-260 МиБ на воркер; peak cgroup 191/387/729/1409 МиБ). Все
   варианты помещаются в `mem_limit 3g` с запасом (8 воркеров ~ 50%).
   Каркас задания может использовать до 8 воркеров; рекомендуем <= 4
   (запас > 2 ГиБ для генератора и студенческого кода).
