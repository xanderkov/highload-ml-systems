# Курс по оптимизации инференса: платформа + раздел «Кэш процессора»

Дата: 2026-08-31
Статус: дизайн утверждён, готов к планированию реализации

## 1. Задача

Курс для инженеров об оптимизации ML-инференса. Обучающийся поднимает у себя
`docker compose up`, открывает страницу и проходит разделы: текст, иллюстрации,
анимации, запускаемые бенчмарки и задания с проверкой ускорения.

Главный тезис курса: иерархия памяти — не деталь низкоуровневого
программирования, а сквозной принцип, который инженер уже применяет в бэкенде
(база → кэш → in-memory) и который точно так же определяет скорость кода на CPU
и на GPU. Курс даёт ментальную модель работы компьютера и доказывает, что писать
быстрый код несложно, если понимать память; в частности — что на Python с NumPy
достигается производительность, ради которой обычно уходят в Go или Rust.

Курс состоит из двух частей: CPU (первая) и GPU (вторая). Настоящий документ
описывает платформу и первый раздел первой части.

## 2. Границы первой итерации

Входит:

- инфраструктура: `docker compose up` поднимает работающий курс;
- движок контента: разделы из Markdown, оглавление, рендер, интерактивные блоки;
- runner: компиляция и исполнение C и Python, замеры, проверка заданий;
- раздел «Память, которую вы уже понимаете» — полностью, включая три задания.

Не входит (последующие итерации):

- остальные разделы части CPU (SIMD, GIL, многопоточность, false sharing);
- часть GPU и исполнение CUDA-ядер;
- аутентификация, серверное хранение прогресса, статистика по студентам.

## 3. Принятые решения и их основания

| Решение | Основание |
| --- | --- |
| Код исполняется на сервере в Docker, не в браузере | Курс держится на доверии к замерам. Нужны настоящие `gcc -O3`, CPython, NumPy с BLAS. В браузере таймеры огрублены, WASM-NumPy без нативного BLAS/SIMD, счётчиков нет. |
| Один студент — один выделенный сервер | Подтверждено заказчиком. Снимает очереди, мультитенантность и борьбу за ядра. |
| Машины студентов идентичны; локальная разработка на ARM Mac | Код и контент архитектурно-нейтральны: сборка нативная под архитектуру хоста (никакой эмуляции QEMU — она уничтожает замеры), размеры кэшей определяются в рантайме, конкретные числа железа не зашиваются в текст. |
| `perf` и PMU-счётчики не используются | Недоступны в Docker Desktop на macOS (виртуализация). Замена — измерение времени в зависимости от размера рабочего множества: график сам показывает границы L1/L2/RAM и работает на любой машине. |
| Свой лёгкий стек вместо Jupyter или React SPA | Jupyter превращает C в `%%writefile` + `!gcc` в самом центре курса про C и лишает контроля над подачей. React добавляет node-сборку в compose ради страницы, которая на 90 % статический текст. |
| Контент в Markdown, `content/` монтируется volume, рендер на запрос | Автор должен править материалы и видеть результат по F5. Пересборка образа на каждую правку текста означает, что материалы перестанут править. |
| Прогресс в `localStorage`, БД нет | Единственный потребитель прогресса — сам браузер студента. Схема миграций ради галочек «раздел пройден» не окупается. |
| Задания проверяются относительным ускорением к baseline из того же прогона | Абсолютный порог («уложись в 5 мс») зависит от железа и загрузки. Отношение к baseline, замеренному тут же, устойчиво. |

## 4. Архитектура

Два сервиса, единственная точка входа — `web`.

```
браузер ──18080──> web ──внутренняя сеть──> runner
                  │                         │
                  │ FastAPI                 │ FastAPI
                  │ рендер Markdown         │ gcc/clang -O3 -march=native
                  │ отдача статики          │ CPython + NumPy (BLAS)
                  │ прокси /api/run         │ подпроцесс: rlimit + timeout
                  └ компилятора нет         └ выхода в интернет нет
```

`runner` не публикует портов и находится в сети с `internal: true`: до него нельзя
достучаться мимо `web`, и из него нельзя сделать `pip install` посреди урока.
Это защита от случайности, а не от злоумышленника — при модели «один студент,
свой сервер» строить seccomp-профили нецелесообразно.

`content/` монтируется в оба сервиса: в `web` — для рендера, в `runner`
read-only — потому что harness'ы заданий живут вместе с материалами.

### Структура репозитория

```
course/
  docker-compose.yml
  Makefile
  web/
    Dockerfile
    app/
      main.py           # маршруты, прокси к runner
      content.py        # сканирование content/, парсинг фронтматтера и блоков
      render.py         # Markdown → HTML, подстановка виджетов
    static/
      app.js  style.css  vendor/   # CodeMirror 6, KaTeX, библиотека графиков
  runner/
    Dockerfile
    app/
      main.py           # POST /run
      sandbox.py        # лимиты, таймауты, tmpfs, уборка
      measure.py        # протокол замера: прогрев, повторы, A/B, медиана
  content/
    01-cpu-cache/
      section.md
      images/
      snippets/
      harness/
  docs/superpowers/specs/
  tests/
```

## 5. Модель контента

Раздел — папка в `content/`. Оглавление собирается сканированием фронтматтера;
отдельного реестра разделов нет намеренно — реестр, который надо править
синхронно с файлами, со временем расходится с ними. Добавленная папка появляется
в оглавлении, удалённая исчезает, `draft: true` скрывает раздел.

```markdown
---
id: cpu-cache
title: Кэш процессора
order: 10
---

Обычный Markdown: заголовки, таблицы, списки, KaTeX для формул.

> [!NOTE]
> Врезки в GitHub-синтаксисе; своего синтаксиса не изобретаем.

![Иерархия памяти](images/hierarchy.svg)
```

Порядок задаётся полем `order` с шагом 10, чтобы вставка раздела между
существующими не требовала перенумерации.

### Интерактивные блоки

Объявляются fenced-блоками — подсветка и редакторы Markdown не ломаются.

````markdown
```viz id=stride-walk
Анимация обхода матрицы по строкам и по столбцам.
```

```benchmark id=row-vs-col lang=c
harness: matrix_sum
variants: [rows, cols]
```

```exercise id=col-sum lang=c
title: Ускорь суммирование по столбцам
target: speedup >= 3
starter: snippets/col_sum_starter.c
reference: snippets/col_sum_ref.c
harness: matrix_sum
```
````

Типы блоков: `viz` (анимация/интерактивная визуализация на JS), `benchmark`
(запуск готовых вариантов, сравнение), `exercise` (редактируемое задание с
проверкой), `sandbox` (свободный редактор без проверки).

Связь блоков с кодом задаётся по имени, без отдельного реестра:

- `benchmark`: каждый элемент `variants` — файл `snippets/<harness>_<variant>.<ext>`.
  Пример: `harness: matrix_sum`, `variants: [rows, cols]` → `snippets/matrix_sum_rows.c`
  и `snippets/matrix_sum_cols.c`. Первый вариант в списке считается baseline,
  остальные сравниваются с ним. Отсутствие файла — ошибка парсинга.
- `viz`: `id` блока соответствует модулю `web/static/viz/<id>.js`, экспортирующему
  функцию `mount(element, params)`. Отсутствие модуля — ошибка парсинга.

Код заданий и примеров лежит в `snippets/*.c` и `snippets/*.py`, а не инлайн в
Markdown: этот код компилируется и прогоняется тестами — инлайн протухнет молча,
файловый сломает сборку. Плюс текст раздела остаётся читаемым при правке.

Иллюстрации — SVG (масштабируются, правятся текстом, живут в обеих темах).
Там, где нужна анимация, используется `viz`-виджет: gif нельзя остановить,
отмотать и пересчитать под другие размеры массива.

## 6. Runner

### Harness

Студент пишет только функцию с фиксированной сигнатурой — не `main()`, не
таймеры, не циклы прогрева. Обвязка отвечает за генерацию данных, прогрев,
повторы, проверку корректности и формирование JSON-результата. Без этого
студент тратит время на boilerplate, а числа получаются случайными.

Harness лежит вместе с материалами:
`content/01-cpu-cache/harness/matrix_sum/{bench.c, meta.yml}` — и монтируется в
runner read-only. Держать harness внутри образа нельзя: тогда добавление задания
требует пересборки.

`meta.yml` задаёт контракт:

```yaml
signature: "double matrix_sum(const double* a, int n)"
cflags: ["-O3", "-march=native"]
sizes: [512, 1024, 2048]
warmup: 3
repeats: 11
timeout_s: 30
tolerance: 1e-9
```

### Протокол замера

1. **Прогревочные прогоны отбрасываются.** Первый прогон меряет холодный кэш,
   page faults и лениво замапленные страницы — что угодно, кроме алгоритма.
2. **Медиана из N повторов, не среднее.** Один вылет планировщика сдвигает
   среднее и не трогает медиану. Разброс показывается студенту рядом с
   результатом, чтобы он видел шум, а не верил единственной цифре.
3. **Baseline и решение чередуются A/B/A/B в одном прогоне.** Последовательный
   прогон «сначала все baseline, потом все решения» отдаёт второму замеру
   фальшивое замедление из-за троттлинга и дрейфа частоты.

`speedup = median(baseline) / median(student)`.

Тот же harness параметризуется размером рабочего множества и возвращает серию
точек для sweep — из неё фронтенд строит «лестницу кэша».

### Вердикт задания

`passed = correct AND (speedup >= target)`.

Корректность проверяется сравнением с эталоном: для float — относительная
погрешность в пределах `tolerance`. Без этой проверки «оптимизация», возвращающая
мусор, засчитывалась бы как победа. Эталонное решение не отдаётся в HTML.

### Изоляция и лимиты

- компиляция — таймаут 10 с;
- исполнение — таймаут из `meta.yml` (по умолчанию 30 с);
- `RLIMIT_AS` на память, `RLIMIT_NPROC`, `RLIMIT_FSIZE`;
- запуск от непривилегированного пользователя;
- рабочая директория в tmpfs, удаляется после прогона;
- сети наружу нет (уровень compose).

Команда компиляции показывается студенту: значительная часть урока про
векторизацию состоит в понимании того, что `-O3` уже сделал сам.

### Ошибки

Сообщения человеческим языком: ошибка компиляции — с номером строки и логом;
таймаут — «не уложился в N с, похоже на бесконечный цикл»; превышение памяти —
явным текстом. Голых кодов возврата студент не видит.

### API

`POST /api/run`

```json
{ "section": "01-cpu-cache", "block": "col-sum", "lang": "c",
  "code": "...", "mode": "exercise" }
```

`mode` принимает `exercise` (замер против baseline, проверка корректности,
вердикт), `benchmark` (прогон вариантов или sweep, без вердикта) и `sandbox`
(исполнение без замера, только вывод). Поля `speedup`, `correct` и `passed`
присутствуют только при `mode: exercise`.

Ответ:

```json
{ "status": "ok",
  "compile_command": "gcc -O3 -march=native ...",
  "baseline_ms": 12.4, "student_ms": 3.9, "spread_pct": 2.1,
  "speedup": 3.18, "correct": true, "passed": true,
  "stdout": "", "stderr": "" }
```

Для `benchmark` со sweep возвращается серия точек `{size, ms_per_element}`.

Python-путь устроен так же: harness `content/<раздел>/harness/<имя>/bench.py`
импортирует функцию студента, меряет
`time.perf_counter`, применяет тот же A/B-протокол — чтобы сравнение «чистый
Python против NumPy» проводилось той же линейкой, что и замеры C.

## 7. Содержание раздела «Память, которую вы уже понимаете»

Контент — на русском; код и идентификаторы — на английском.

1. **Крючок: вы это уже знаете.** Postgres → Redis → локальный dict в процессе;
   инженер уже принимает решения по этой модели. Поворот: тот же рисунок
   существует на шесть порядков ниже — RAM → L3 → L2 → L1 → регистры.
   Латентности в человеческих единицах: если попадание в L1 — одна секунда, то
   поход в RAM — около трёх минут.
2. **Первый замер: лестница.** `viz` + `benchmark`: обход массива, sweep по
   размеру рабочего множества. На графике три полки. Студент сам находит границы
   L1 и L2 своей машины по излому кривой и сверяет с тем, что рапортует железо.
3. **Почему полки: кэш-линия.** Память ездит блоками по 64 байта. Последовательный
   и случайный обход одного объёма различаются на порядок при том же количестве
   арифметики: «объём работы» и «время работы» — разные вещи.
4. **Задание 1 (C): суммирование матрицы по столбцам.** Порог `speedup >= 3`.
   Решение — переставить вложенные циклы; одна строка. Доказательство тезиса
   «несложно»: не переписать на Rust, а понять раскладку памяти.
5. **Prefetcher.** График времени от шага доступа: после 64 байт выход на плато.
   Процессор угадывает предсказуемый паттерн и сдаётся на случайном.
6. **Задание 2 (C): блочное умножение матриц.** Наивные три цикла против
   тайлинга, порог `speedup >= 2`. Здесь студент впервые проектирует под кэш и
   обнаруживает, что оптимальный размер тайла упирается в размер L1, измеренный
   в пункте 2.
7. **Мост в Python.** Тот же цикл на чистом Python — в сотню с лишним раз
   медленнее. Причина не «Python интерпретируемый» (ответ, который ничего не
   объясняет), а: каждое число — объект в куче, элементы списка — указатели в
   произвольные адреса. Python по устройству ломает локальность.
8. **NumPy как прямое следствие.** `ndarray` — непрерывный блок памяти с типом,
   то есть именно то, что любит кэш; тот же цикл через NumPy вплотную подходит к
   C. И сразу: у NumPy тоже row-major — `sum(axis=0)` и `sum(axis=1)` стоят
   разного. **Задание 3 (Python)**: ускорить обработку выбором оси и устранением
   лишних копий.
9. **Вывод и мост в часть 2.** Незачем уходить в Go или Rust — нужно понимать
   память; NumPy написан людьми, потратившими на это годы, и теперь им можно
   пользоваться осознанно. У GPU иерархия та же, только правила жёстче.

## 8. Тестирование

Реализация ведётся по TDD.

**Парсер контента.** Фронтматтер, сборка оглавления, каждый тип блока. Отдельно —
что парсер падает громко: неизвестный тип блока, `starter:` на несуществующий
файл, отсутствующий `harness:`. Молчаливо проглоченная опечатка означает пустое
место на странице и полчаса недоумения автора.

**Runner.** Успешная компиляция; ошибка компиляции возвращает лог с номером
строки; таймаут ловится; превышение памяти ловится; неверный результат помечается
некорректным несмотря на высокий speedup; расчёт speedup из серии замеров.

**Материал курса.** Для каждого задания два теста: эталонное решение проходит
свой порог, а стартовый код его не проходит. Первый ловит протухший harness и
завышенный порог, второй — задание, которое решается само собой и ничему не учит.
Это performance-тесты, они шумные, поэтому вынесены в отдельную команду
`make verify-content` и гоняются на целевой машине, а не в общем юнит-прогоне:
флакающие тесты в общем прогоне рано или поздно отключают.

**Smoke.** `docker compose up` → страница отвечает, раздел рендерится, `/api/run`
возвращает валидный результат.

## 9. Критерии готовности

- `docker compose up` на чистой машине даёт работающий курс без ручных шагов;
- раздел «Память, которую вы уже понимаете» проходится целиком;
- три задания проверяются, эталоны проходят, стартовый код — нет;
- график лестницы кэша воспроизводимо показывает границы уровней;
- правка `section.md` видна после перезагрузки страницы, без пересборки образа;
- юнит-тесты зелёные; `make verify-content` зелёный на целевой машине.
