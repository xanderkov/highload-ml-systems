# Курс по инференсу: раздел «Triton: проверяем обещания замером»

Дата: 2026-11-08
Статус: подход и план глав согласованы в обсуждении, ожидает ревью спеки

## 1. Контекст и задача

Продолжение раздела `content/30-naive-service/` (спека
`2026-11-01-naive-service-section-design.md`). Сюжет курса:

> рантайм Python → наивный сервис + свой батчер → **Triton** → (бонус) LLM.

Раздел 30 закончился списком: что мы сделали руками (поток для модели,
бинарный протокол, воркеры и потоки, очередь и сбор батча, подбор
`max_batch_size`/`max_queue_delay`) и чего не сделали (ошибка одного входа
валит батч, отменённый клиент занимает место, неограниченная очередь без
backpressure, одна модель и одна версия, нет метрик). Там же открытый вопрос:
на одном экземпляре модели и CPU ожидание в очереди (`max_queue_delay`) не
окупилось; гипотеза — окупается при нескольких экземплярах.

Этот раздел ставит **ту же `widemodel`** в Triton, подаёт **ту же нагрузку**
тем же генератором при тех же 3 CPU и замерами отвечает: какие боли Triton
снимает, какие частично, что по-прежнему настраивается руками.

Железо: CPU-only. Принцип раздела: сначала замер, потом вывод; формулировки
«в нашем замере», никаких непроверенных технических утверждений.

## 2. Границы

Входит:

- раздел `content/40-triton/` (`order: 40`): текст, эксперименты, два задания;
- сервис `triton` в `docker-compose.yml` (тонкий `triton/Dockerfile` поверх
  образа NGC) и общий том репозитория моделей;
- библиотека `content/40-triton/harness/_lib/tritonlib.py` (загрузка/выгрузка
  модели, тело запроса KServe v2, метрики, блокировка сервера);
- копии `servicelib.py` и `widemodel.py` из раздела 30 (§5.5).

Не входит:

- GPU, ONNX Runtime, TensorRT, ансамбли и BLS;
- gRPC-клиент (только HTTP: тот же сырой генератор, честное сравнение с
  разделом 30);
- студенческий Python-код внутри контейнера Triton (§3);
- LLM-бонус — отдельный подпроект.

## 3. Принятые решения и основания

| Решение | Основание |
| --- | --- |
| Один общий сервис `triton` в compose, `--model-control-mode=explicit` | Настоящий Triton, без docker-сокета в runner (это был бы выход из sandbox). Модель загружается и выгружается на задание через `/v2/repository/models/<name>/load|unload` — дешевле перезапуска сервера. |
| Сервер прибит к 3 CPU (`cpuset`, по умолчанию `1-3`, переменная `TRITON_CPUS`), генератор в runner — к CPU 0 | Тот же бюджет, что `SERVICE_MAX_CPUS` в разделе 30, иначе сравнение нечестное. Генератор не делит CPU с сервером. |
| Задания пишут только `config.pbtxt` и скрипт экспорта; `model.py` python backend — наш | Студенческий код не исполняется внутри Triton, где нет лимитов runner. Экспорт исполняется в обычном sandbox runner. |
| Сначала python backend, потом libtorch | Мост от раздела 30 (тот же torch-код), затем отдельный замер: что даёт уход от интерпретатора. Один шаг — одно изменение. |
| Замеры на сервере — под файловой блокировкой (`flock` в общем томе) | Runner не сериализует задания; два параллельных замера на одном сервере исказили бы друг друга. Ждущий замер пишет «сервер занят другим замером». |
| Уникальное имя модели на задание (`<блок>-<pid>-<случайное>`), выгрузка в `finally` | Повторный запуск не видит состояние прошлого, упавший харнесс не оставляет модель загруженной: под блокировкой других замеров нет, поэтому перед `deploy` харнесс выгружает все загруженные модели. |
| Протокол — KServe v2 HTTP с binary tensor extension | Сопоставим с бинарным протоколом раздела 30; JSON-вариант показывается один раз как цена текста, а не как основной путь. |

## 4. Содержание раздела

Каждая подглава: короткий текст → блок замера → вывод из цифр. Конкретные
RPS, SLO и пороги — калибровка (§7), ниже — что меряем и что ожидаем
проверить, а не что утверждаем.

### 0. Крючок: «Triton не магия»

`widemodel` в python backend с минимальным `config.pbtxt` (без
`dynamic_batching`, один экземпляр). Те же ступени нагрузки, что в крючке
раздела 30. Проверяем: ведёт ли себя как батч из одного раздела 30 (ожидание —
да: без конфигурации батчинга Triton исполняет запросы по одному). Вывод:
Triton — набор механизмов, которые включаются конфигурацией.

### 1. Репозиторий моделей, `config.pbtxt`, протокол

Структура `model_repository/<name>/config.pbtxt` + `<version>/model.py`;
входы/выходы, `max_batch_size`, `KIND_CPU`. Протокол KServe v2: JSON-тело
против binary extension на одной ступени нагрузки — та же «цена текста», что в
разделе 30, теперь у Triton. Сравнение с бинарным сервисом раздела 30 при
равной нагрузке (latency p50/p99).

### 2. `dynamic_batching` против своего батчера

Включаем `dynamic_batching { }` и сравниваем с эталонным батчером раздела 30
при 700 RPS, SLO 50 мс (goodput, p99, средний реальный размер батча из
метрик Triton).

**Задание 1** (`kind: ab`, `lang: protobuf`): студент пишет `config.pbtxt`.
Порог — тот же характер, что в задании раздела 30: goodput при SLO не ниже
порога относительно стартового конфига (без батчинга); ответы проверяются по
входам (каждый ответ — от своего входа). Типовые ошибки, которые должны
ловиться понятным сообщением: конфиг не загружается (показываем ошибку
загрузки из Triton), `max_batch_size: 0` при включённом батчинге, огромный
`max_queue_delay_microseconds` (не проходит SLO на редкой нагрузке).

### 3. `instance_group` × `max_queue_delay`

Открытая проверка раздела 30. Сетка: экземпляров 1/2/3 × задержка 0/…/N мкс
при 100 и 700 RPS. Потоки `torch` на экземпляр — ручная ручка
(`parameters` python backend / переменные окружения), её произведение с числом
экземпляров не должно превышать 3 CPU — это показываем замером, а не
утверждаем. Вывод — каким бы он ни вышел в замере, включая «не окупается и
здесь».

### 4. Python → libtorch

Экспорт `widemodel` в TorchScript, `platform: "pytorch_libtorch"`, тот же
батчинг. Сравнение python backend и libtorch при одинаковом конфиге. Модель
упирается в чтение весов, поэтому выигрыш может быть малым — пишем ровно то,
что намерили.

**Задание 2** (`kind: ab`, `lang: python`): студент пишет функцию экспорта
(`torch.jit.trace`/`script`) и конфиг под libtorch. Проверка: модель
загружается, ответы совпадают с эталонной `widemodel` (допуск по float),
батч разных размеров работает (не зашит размер трассировки), goodput не ниже
порога. Типовые ошибки: трассировка с зашитым батчем 1, неверные имена
входов/выходов (`INPUT__0`/`OUTPUT__0`). (Забытый `eval()` не ловится: у `widemodel` нет dropout/batchnorm.)

### 5. Пять болей, проверка по списку

Каждый пункт — короткий замер или демонстрация:

- **backpressure**: перегрузка ×1,5 ёмкости с неограниченной очередью и с
  `default_queue_policy { max_queue_size, timeout_action: REJECT }` — latency
  принятых запросов и доля отказов;
- **ошибка одного входа в батче**: вход, на котором наш `model.py` бросает
  исключение (флаг во входе), в батче с нормальными — кто получил ошибку;
- **отменённый клиент**: клиенты, рвущие соединение до ответа, — занимают ли
  они место в батче (по метрикам выполненных запросов); если Triton это не
  снимает в нашем замере — так и пишем;
- **несколько моделей и версий**: вторая версия загружается рядом без
  остановки, нагрузка на первую в это время — без ошибок;
- **метрики**: Prometheus на `:8002` — время в очереди, время вычисления,
  реальный размер батча (`nv_inference_count` против
  `nv_inference_exec_count`).

### 6. Вывод и мост к LLM

Таблица «боль → снята / частично / руками», по цифрам глав 0–5. Что
осталось руками (потоки × экземпляры, выбор задержки, экспорт). Мост:
батчинг запросов целиком не подходит генерации, где ответы разной длины —
отсюда continuous batching в бонусе.

## 5. Платформа

### 5.1. Сервис `triton`

- `triton/Dockerfile`: `FROM nvcr.io/nvidia/tritonserver:<тег>-py3` + CPU-сборка
  `torch` для python backend; тег фиксируется в спайке (§7.1).
- compose: сеть `back` (internal), `cpuset: ${TRITON_CPUS:-1-3}`,
  `mem_limit`, команда `tritonserver --model-repository=/models
  --model-control-mode=explicit`, healthcheck на
  `/v2/health/live`; `runner` зависит от `triton` (healthy).
- Том `model_repo`: в `triton` — `/models` (только чтение), в `runner` —
  `/models` (запись); там же файл блокировки.
- Порт наружу не публикуется: только runner ходит к серверу.

### 5.2. `tritonlib.py`

- `server_lock()` — контекст, `flock` на `/models/.lock`;
- `deploy(name, files: dict[str, bytes]) -> контекст`: пишет репозиторий,
  `load`, ждёт ready; при ошибке загрузки — `TritonLoadError` с текстом
  Triton; в `finally` — `unload` и удаление папки;
- `v2_body(array, *, binary=True) -> (bytes, headers)` для генератора
  `servicelib.run_load` (нужен параметр заголовков запроса —
  `Inference-Header-Content-Length`; добавляется в `servicelib` без
  изменения поведения раздела 30);
- `parse_v2_response(bytes) -> np.ndarray` для проверки ответов;
- `metrics(name) -> dict` — разбор Prometheus-текста по модели, дельта за
  ступень (очередь, вычисление, inference_count, exec_count, request_success).
- CPU сервера: из метрик Triton, если версия их отдаёт (проверка в спайке),
  иначе CPU в графиках раздела не показываем.

### 5.3. Харнессы

По образцу раздела 30: `series` для экспериментов, `ab` для заданий;
сервер — через `deploy` под `server_lock`, нагрузка — `servicelib.run_load`
с генератором на CPU 0. `model.py` python backend лежит в `_lib/` и
копируется в репозиторий при `deploy`.

### 5.4. Ограничения runner

Задание 2 экспортирует модель внутри sandbox runner (torch есть). Файл
`.pt` (~112 МиБ) пишется во `/work` (tmpfs 512 МиБ) и копируется харнессом в
том `model_repo`; размер проверяется до копирования.

### 5.5. Копии библиотек раздела 30

`servicelib.py` и `widemodel.py` копируются в `40-triton/harness/_lib/` с
комментарием об источнике (`_lib` разделов независимы, как с `tinymodel` в
разделе 30). Тест проверяет, что копии побайтно совпадают с оригиналом
(кроме явно разрешённых изменений — их нет: доработка заголовков вносится в
оба файла).

## 6. Тестирование

- **Unit (runner)**: `tritonlib` — `v2_body`/`parse_v2_response` туда-обратно,
  разбор Prometheus-текста и дельта, блокировка (второй держатель ждёт);
  `servicelib.run_load` с заголовками.
- **Integration (`make verify-content`, нужен сервис `triton`)**: deploy
  загружает и выгружает модель; битый конфиг даёт `TritonLoadError` с текстом;
  эталоны заданий проходят порог, стартовые — нет; типовые ошибки §4
  ловятся своими сообщениями.
- **Web**: раздел рендерится, блоки известны (существующие тесты).
- **Копии**: `servicelib.py`/`widemodel.py` совпадают с разделом 30.

## 7. Открытые вопросы

1. **Решено (спайк 2026-11-08, машина разработки, 16 CPU).**
   - Образ: `nvcr.io/nvidia/tritonserver:26.10-pyt-python-py3` (только
     python и pytorch backend, 12 ГБ). Своего `torch` для python backend в нём
     нет: `pip install --index-url https://download.pytorch.org/whl/cpu
     "torch~=2.15" "numpy<2"` (флаг `--break-system-packages`), итог 13,3 ГБ.
   - **nvcr.io из РФ отдаёт 403** (реестр и каталог NGC). На машине разработки
     решено правилом прокси на роутере для `nvcr.io` и `nvidia.com`. Студентам
     в той же ситуации нужен VPN или зеркало — README говорит об этом прямо.
     PyPI-пакет `tritonserver` (2.74.0) — только in-process биндинги
     (276 КБ), сервера в нём нет.
   - CPU-only работают оба backend: сервер стартует за ~1 с, python-модель
     грузится ~3,4 с, libtorch ~0,05 с (0,12 с при 3 экземплярах); ответы
     совпадают с eager `widemodel` (`allclose`, 1e-4) на батче 7.
   - Экспорт: `torch.jit.trace` в torch 2.15 работает, но помечен deprecated
     (FutureWarning: «switch to torch.compile or torch.export») — глава 4
     говорит об этом. Файл `model.pt` — 118 МБ.
   - Explicit load/unload чист: 30 циклов со сменой модели, числа
     экземпляров (1/3) и `dynamic_batching` — конфиг каждый раз новый
     (`/v2/models/<n>/config`), 0 неверных ответов из 1500, память сервера
     после выгрузки ~345 МиБ (до циклов 650 МиБ). Вариант B не нужен.
     **Unload асинхронный**: ответ приходит, когда модель ещё `UNLOADING`, а
     процесс-заглушка python backend живёт ещё несколько секунд — `deploy`
     ждёт состояния `UNAVAILABLE` в `/v2/repository/index`.
   - Метрики CPU-only есть: `nv_cpu_utilization`, `nv_cpu_memory_used_bytes`;
     по модели — `nv_inference_request_success`, `nv_inference_count`
     (элементов), `nv_inference_exec_count` (запусков модели),
     `nv_inference_queue_duration_us`, `nv_inference_compute_infer_duration_us`,
     `nv_inference_request_failure{reason=…}` (OTHER/BACKEND/CANCELED/REJECTED),
     `nv_inference_pending_request_count`. Средний батч = `nv_inference_count /
     nv_inference_exec_count`.
   - Потоки torch на экземпляр python backend: `parameters { key:
     "TORCH_THREADS" value { string_value: "3" } }`, читается в `initialize`
     из `args["model_config"]` — проверено (`torch.get_num_threads()` 1 и 3).
     Для libtorch — параметр backend `INTRA_OP_THREAD_COUNT` (проверяется в
     задаче главы 4).
2. Калибровка: ступени, SLO, пороги заданий, сетка подглавы 3 — по замерам
   на машине разработки (16 CPU, серверу 3), таблица как §7.x раздела 30.
3. Поддерживает ли редактор блоков подсветку `protobuf`; если нет —
   `lang: text`.
