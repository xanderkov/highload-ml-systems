# Курс по инференсу: раздел «LLM: батч из шагов, а не из запросов»

Дата: 2026-11-08
Статус: подход, главы и задания согласованы в обсуждении, ожидает ревью спеки

## 1. Контекст и задача

Бонусная часть после раздела `content/40-triton/` (спека
`2026-11-08-triton-section-design.md`). Сюжет курса:

> рантайм Python → наивный сервис + свой батчер → Triton → **(бонус) LLM**.

Раздел 40 закончился «мостом к LLM»: всё держалось на допущении «один запрос —
один вызов модели, батч заканчивается одновременно». Генерация текста — цикл
из десятков–сотен шагов, ответы разной длины; серверы LLM собирают батч из
шагов (continuous batching) и держат память под KV-кэш.

Этот раздел повторяет арку 30→40 на генерации: **сначала боль на своём
цикле**, свой continuous batching руками, потом настоящий сервер —
**llama.cpp** — и проверка замером, что он делает то же и чем его ручки
управляют. vLLM — необязательный блок для машин, где он помещается; SGLang —
в тексте, с нашим замером.

Железо: CPU-only (сервису 3 CPU, генератор нагрузки на CPU 0). Принцип:
сначала замер, потом вывод; формулировки «в нашем замере», никаких
непроверенных технических утверждений.

## 2. Границы

Входит:
- своя крошечная GPT в `_lib` (torch, случайные веса, жадная генерация),
  KV-кэш и `KVBatch` как готовые инструменты;
- замеры: цена шага от размера батча, генерация без кэша и с кэшем,
  статический батч, свой continuous batching, llama.cpp при разном числе
  слотов, бюджет KV, длинный промпт против декода, vLLM (необязательно);
- два задания: движок continuous batching (Python) и бюджет KV в llama.cpp.

Не входит:
- качество текста, сэмплинг (только greedy), токенизаторы как тема;
- квантизация как тема (GGUF q8 — данность, одна фраза в тексте);
- GPU, PagedAttention изнутри, speculative decoding, prefix caching как
  отдельные главы — упоминание в выводе максимум;
- SGLang как сервис в compose (замер спайка — в тексте).

## 3. Принятые решения и основания

| Решение | Основание |
|---|---|
| Основной сервер — llama.cpp | Спайк §7.1: стартует за 1 с, 0,3 ГБ, CPU-бэкенды от sse42 до avx512 выбираются сами — работает у любого студента |
| vLLM — необязательный блок, профиль compose `vllm` | Лучший continuous batching в спайке (~14×), но bf16 требует AVX-512, fp32 нужно ≥6 ГБ и `--enforce-eager`; у студентов Docker на 8 ГБ, из них 4 у Triton |
| SGLang — только текст | В спайке слабейший на CPU: задержка растёт с 4 RPS, потолок ~310 ток/с |
| Свой цикл — крошечная GPT, не Qwen через transformers | Без загрузок, шаг в миллисекундах, KV-кэш и цикл видны целиком; корректность проверяется сравнением с генерацией без батча |
| `KVBatch` даёт библиотека, студент пишет планировщик | Урок — планирование по шагам, а не арифметика паддингов и масок |
| llama-server — подпроцесс харнесса, бинарь в образе runner | `-np`/`-c` меняются только перезапуском; старт 1 с, перезапуск на каждый замер дешёв; так же раздел 30 поднимает свои сервисы |
| Порядок А: своя боль → свой фикс → сервер | Тот же принцип «сначала замер боли», что в 30→40 |

## 4. Содержание раздела

Файл `content/50-llm/section.md`, front matter: `id: llm`, заголовок
«LLM: батч из шагов, а не из запросов», `order: 50`. Карточка «скоро» на
главной убирается (раздел становится ссылкой). Раздел 40, «Мост к LLM» —
ссылка на этот раздел.

### 0. Генерация — это цикл
Блок-замер: время одного шага декода крошечной GPT при батче 1, 2, 4, …, 32
(KV одинаковой длины). Ожидаемая картина (уточнит калибровка): шаг при батче
16 стоит немногим дороже шага при батче 1 — это и есть запас, ради которого
весь раздел. Плюс ток/с одного запроса.

### 1. KV-кэш
Блок-замер: время на токен без кэша (каждый шаг пересчитывает весь префикс)
и с кэшем, по длине ответа 16…512. Вторая линия — память KV на запрос от
длины (байт на токен = 2 × слои × d_model × 4 байта для нашей модели;
формула и число — в тексте). Вывод: кэш делает шаг дешёвым, но платим памятью,
и память ограничивает, сколько запросов можно держать одновременно — это
вернётся в главе 5.

### 2. Статический батч
Блок-замер на открытой нагрузке (80 % коротких ответов, 20 % длинных):
по одному запросу против статического батча (взяли до `max_batch` запросов,
крутим, пока не закончится самый длинный). Линии: время до первого токена
(TTFT) и e2e коротких по RPS. Боль: короткие ждут длинных, новые ждут
освобождения всего батча.

### 3. Задание 1: continuous batching
Тип `ab`, Python. Студент пишет:

```python
def engine(model, inbox, max_batch):
    """Крутится, пока харнесс не закроет inbox. Между шагами:
    принять новые запросы (без ожидания, пока есть место), prefill,
    добавить в KVBatch; один decode_step; отдать каждому его токен;
    убрать закончившиеся строки."""
```

Стартовый код — статический батч (работает, но проигрывает). Проверки:
1. **корректность** — каждый ответ потокен совпадает с генерацией этого же
   запроса в одиночку (ловит перепутанные строки, забытый `keep`);
2. **нагрузка** — смесь 80/20 при откалиброванном RPS: p99 TTFT коротких
   ≤ цели и goodput ≥ 0,9 эталонного движка.
Ошибки, на которые даётся подсказка: «за N с не пришло ни одного токена»
(забыли убрать закончившиеся или принять новые), несовпадение токенов с
номером запроса.

После задания — блок «свой движок против статического батча» (редактируемый,
как в разделе 40 глава 2: берёт код из задания, стартует со стартового).

### 4. llama.cpp: то же, но готовое
Слоты (`-np`) = максимальный размер батча; `-c` — общий бюджет KV-токенов,
делится между слотами. Блок-замер: та же смесь при `-np` 1/4/16, линии TTFT и
ток/с. Второй блок — llama.cpp против своего движка: ток/с одного запроса и
потолок. Честная оговорка в тексте: llama.cpp — C++ и модель q8, наша —
torch fp32 и другая архитектура; сравниваем форму кривых, не абсолютные
числа.

### 5. Задание 2: бюджет KV
Тип `ab`, Python-блок из двух чисел:

```python
SLOTS = 32
CTX_TOTAL = 8192  # не больше KV_BUDGET
```

Смесь с длинными ответами (промпт + ~512 токенов). Ловушки: много слотов →
`CTX_TOTAL / SLOTS` меньше длинного ответа → ответ обрезан или отклонён
(точное поведение llama.cpp — §7, калибровка); мало слотов → очередь, TTFT
взрывается. Проверки: нет обрезанных ответов (число токенов = запрошенному),
`CTX_TOTAL ≤ KV_BUDGET`, goodput ≥ цели при откалиброванном RPS.

### 6. Длинный промпт и остальное
- Блок-замер: идёт поток коротких генераций, в момент t подаётся один
  промпт на ~1500 токенов; линия — время между токенами у остальных по
  времени. Пик — prefill чужого промпта; в тексте — chunked prefill и что
  у llama.cpp за это отвечает (`-b`/`-ub`, проверить в калибровке).
- Необязательный блок vLLM: если сервис `vllm` запущен — та же смесь, что в
  главе 4; иначе — «не запущен, вот как и зачем» (AVX-512, память).
- SGLang: абзац с нашим замером спайка.
- Таблица вывода: что сделали руками / что делает сервер / что ещё
  настраивается. Финал курса.

## 5. Платформа

### 5.1. Образ runner
- Multi-stage: `COPY --from=ghcr.io/ggml-org/llama.cpp:server-b12199 /app
  /opt/llama` — бинарь `llama-server` и его `.so` (включая CPU-бэкенды);
  `LD_LIBRARY_PATH=/opt/llama`. Бинарь собран под Ubuntu 24.04, runner на
  `python:3.12-slim` — совместимость glibc/libstdc++ проверяется первым
  шагом плана (§7).
- GGUF модели скачивается при сборке: `Qwen/Qwen2.5-0.5B-Instruct-GGUF`,
  файл `qwen2.5-0.5b-instruct-q8_0.gguf` (~0,7 ГБ), в `/opt/models`. Рост
  образа замеряется и попадает в README.
- `llama-server` работает под ограничениями sandbox (RLIMIT_AS ≤ 2048 МБ,
  NPROC 256) — проверяется калибровкой; при нехватке — meta `memory_mb` блока.

### 5.2. Сервис `vllm` (необязательный)
`docker-compose.yml`: `vllm/vllm-openai-cpu:v0.33.0`, `profiles: [vllm]`,
cpuset `${TRITON_CPUS:-1-3}`, `mem_limit: 6g`, `shm_size: 1g`,
`VLLM_CPU_KVCACHE_SPACE=1`, `VLLM_CPU_OMP_THREADS_BIND` = те же CPU,
`--dtype bfloat16 --max-model-len 2048`, модель — HF-снапшот
`Qwen/Qwen2.5-0.5B-Instruct` в томе (скачивается при первом старте).
Triton и vLLM вместе на одни CPU не запускаются — README говорит
остановить Triton.

### 5.3. `_lib` раздела 50
- `tinygpt.py` — модель (декодер, RoPE или learned pos, causal attention),
  фиксированный seed; `prefill(tokens) -> (logits, kv)`,
  `decode_step(kvbatch, last_tokens) -> logits`; размер (≈4 слоя × d=256,
  словарь ~1000) подбирается калибровкой так, чтобы шаг при батче 1 был
  несколько мс и батч давал выигрыш.
- `KVBatch` — тензоры K/V с паддингом, длины строк, маска;
  `add(kv_one)`, `keep(rows)`, `__len__`.
- `generate_alone(model, prompt, n)` — эталон для проверки корректности.
- `llmload.py` — открытая нагрузка со стримингом (asyncio, без внешних
  зависимостей, как спайковый `load.py`): TTFT, межтокенное время, e2e по
  классам, ошибки, обрезанные ответы; клиент для своего движка (внутри
  процесса через `inbox`) и для OpenAI-совместимого `/v1/completions`
  (llama.cpp, vLLM).
- `llama.py` — `serve(slots, ctx_total, cpus) -> url` (контекстный
  менеджер: старт, ожидание `/health`, при ошибке старта — хвост stderr в
  сообщении, остановка в `finally`).
- `stand.py` — общий лок замеров (как в разделе 40), разбиение CPU,
  повтор при отставании генератора.

### 5.4. Харнессы
`hook` (глава 0), `kv_cache`, `static`, `engine_exercise`, `engine_vs_static`,
`llama_slots`, `llama_vs_engine`, `kv_budget_exercise`, `long_prompt`,
`vllm`. Каждый `bench.py` заканчивается `with stand.exclusive(): main()`.
Таймауты ≤ 240 с.

### 7.1. Спайк (2026-11-08, Ryzen 7 7700, серверу CPU 1–3, генератор CPU 0)
Qwen2.5-0.5B-Instruct, открытая нагрузка: 80 % ответов по 16 токенов, 20 % —
по 128, `ignore_eos`, 15 с на ступень.

| | vLLM bf16 | vLLM fp32 eager | SGLang bf16 | llama.cpp q8 |
|---|---|---|---|---|
| Старт | 69 с | 24 с | 18 с | 1 с |
| Один запрос, ток/с | ~41 | ~21 | ~26 | ~89 |
| Потолок, ток/с | ~580 | ~316 | ~310 | ~260 |
| Рост задержки с | ~16 RPS | ~16 RPS | 4 RPS | ~8 RPS |
| Память | 5,2 ГБ | 6 ГБ (4 ГБ — не стартует) | упёрся в 6 ГБ | 0,3 ГБ |

vLLM fp32 без `--enforce-eager` не стартовал: после компиляции оставалось
0,38–0,72 ГБ под KV при лимите 4–6 ГБ. vLLM на CPU без AVX-512 не проверен
(на машине разработки он есть). Версии: vLLM v0.33.0, SGLang v0.5.23-xeon,
llama.cpp build 12199.

### 7.2. Ответы на вопросы 1, 2, 4, 5 (задача 1 плана, 2026-11-08)
1. **Решено.** `llama-server` b12199 из образа Ubuntu 24.04 работает в
   `python:3.12-slim` после `apt-get install libgomp1`; больше ничего не
   нужно. Рост образа runner: +47 МБ (`/opt/llama`) + 676 МБ (GGUF q8)
   + <1 МБ (libgomp) ≈ 724 МБ; образ — 3,36 ГБ.
2. **Решено.** Слот `-np 4 -c 1024` (256 токенов на слот), промпт 3 токена:
   `max_tokens=200` → 200 токенов; `max_tokens=512` → HTTP 200,
   `finish_reason: "length"`, `completion_tokens: 253` — **молча обрезано**
   до размера слота. Промпт длиннее слота → HTTP 400,
   `exceed_context_size_error`. Проверка задания 2: `completion_tokens <
   max_tokens` = обрезанный ответ.
4. **Решено.** Под RLIMIT_AS 2048 МБ при `-np 32`: `-c 32768` стартует,
   `-c 65536` — нет (`libgomp: Thread creation failed`). `KV_BUDGET ≤ 32768`.
5. **Решено.** 4 потока коротких генераций, `-np 8 -c 8192`, в момент t
   один промпт на 888 токенов (prefill ~560 ток/с, 592 токена — 1,06 с):

   | флаги | prefill длинного | межтокенное у коротких, p50 / max |
   |---|---|---|
   | по умолчанию | 1,63 с | 23 мс / 1606 мс |
   | `-ub 64` | 1,83 с | 23 мс / 1815 мс |
   | `-b 64 -ub 64` | 2,51 с | 23 мс / 201 мс |

   Пауза декода чужих запросов управляется `-b` (логический батч), не
   `-ub`; цена — длинный промпт обрабатывается дольше. Глава 6 сравнивает
   «по умолчанию» и `-b 64 -ub 64`.

### 7.3. Калибровка (дописывается по задачам плана; CPU 1–3, 3 потока torch)

**tinygpt** (задача 2), шаг декода при KV 64, медиана 20 шагов:

| размер | параметров | b1 | b4 | b16 | b32 |
|---|---|---|---|---|---|
| 4 × 256, словарь 1024 | 3,9 M | 0,62 мс | 0,80 | 1,54 | 2,40 |
| 6 × 384, словарь 1024 | 11,8 M | 2,87 мс | 2,76 | 4,54 | 6,75 |
| **8 × 512, словарь 4096** (DEFAULT) | 29,9 M | 5,90 мс | 5,90 | 9,09 | 13,80 |

DEFAULT выбран так, чтобы шаг при батче 1 был в 2–8 мс, батч 16 стоил ≤ 2,5×
батча 1, а поток токенов между процессами оставался умеренным.

**Глава 0** (`llm-hook`, KV 64, медиана 20 шагов): шаг b1 6,00 мс (167 ток/с),
b2 5,18, b4 6,01, b8 6,97, b16 9,05 (1768 ток/с), b32 13,92 мс (2299 ток/с);
мс на токен 6,00 → 0,435 (в 13,8 раза дешевле). Веса ~120 МБ (29,9 M × 4 байта).

**Глава 1** (`llm-kv-cache`, промпт 16): мс на токен без кэша / с кэшем —
16: 9,70 / 6,76; 32: 11,79 / 6,42; 64: 14,08 / 6,45; 128: 20,65 / 6,45;
256: 33,8 / 6,5; 512: 62,45 / 6,52. KV на токен 32 КиБ; кэш запроса 16+512 —
16,5 МиБ. Прогон блока ~52 с.
