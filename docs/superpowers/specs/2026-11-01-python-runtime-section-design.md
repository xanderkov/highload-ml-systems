## 1. Контекст и задача

Курс продолжает существующий курс «CPU-оптимизация» (репозиторий `cpu-course`,
спека `docs/superpowers/specs/2026-08-31-inference-course-design.md`). Используются
та же платформа (`web` + `runner`, Markdown-разделы, блоки `viz`/`benchmark`/
`experiment`/`exercise`), тот же протокол замера (прогрев, медиана, чередование
A/B) и тот же формат заданий с проверкой относительно baseline.

Сюжет курса целиком:

> CPU-кэш → память и рантайм Python → наивный сервис FastAPI + torch →
> Triton → (бонус) LLM: continuous batching, KV-cache, SGLang.

Главный тезис новой части: каждый шаг к Triton обоснован болью, которую студент
**сам замерил**. Утверждение «Triton хороший» не принимается без замера: сначала
показываем, что ломается в наивном сервисе и почему.

Железо: основной сценарий только CPU, GPU-лабы опциональны. Отсюда
лёгкие модели, создаваемые в коде, и честные эффекты на CPU.

## 4. Содержание раздела

Контент на русском; код и идентификаторы на английском. Структура подглав

### 0. Крючок: «мы же ничего не писали»

`benchmark` без вердикта. Родитель загружает «токенизатор» — `dict` примерно
на 1M строковых ключей (~300 МБ), — затем делает fork на 4 воркера. Воркеры
только читают словарь. График PSS каждого воркера во времени: память растёт,
и суммарно получаются почти четыре копии.

> Воркеры ничего не записывали. Откуда копии?

### 1. Почему чтение — это запись

- В заголовке каждого объекта есть `ob_refcnt`, у контейнеров ещё и GC-заголовок.
  `x = vocab[k]` увеличивает refcount, то есть пишет в страницу памяти.
- Copy-on-write копирует страницу целиком (4 КиБ). Мелкие объекты разбросаны по
  страницам, поэтому со временем копируется почти всё.
- `viz id=cow-pages`: страницы родителя и ребёнка; обращение к объекту
  «пачкает» его страницу, и она копируется.
- Важный нюанс, подтверждаемый замером: **данные torch-тензора остаются
  общими**. Refcount живёт в маленьком Python-объекте, а storage с весами
  не трогается. Ловушка в Python-объектах (словари, списки, метаданные),
  а не в весах модели.
- Immortal objects (Python 3.12, PEP 683): касаются `None`, малых int и
  интернированных строк, пользовательские объекты не спасают.

**Задание 1 (Python)**: снизить прирост PSS воркеров.
`target: pss_growth_ratio <= 0.3`. Эталонное решение: компактное хранение
(отсортированные хэши ключей + значения в numpy-массивах, поиск через
`np.searchsorted`) вместо `dict` Python-объектов. `gc.freeze()` разбирается в
тексте и проверяется в эксперименте как **частичная** мера: он избавляет от
записей сборщика мусора в GC-заголовки, но не от инкрементов refcount, поэтому
сам по себе порог не берёт (это фиксируется калибровкой). Корректность:
воркеры возвращают контрольную сумму прочитанных значений, она совпадает с
эталоном.

Определение метрики: `pss_growth_ratio = (Σ PSS воркеров в конце − Σ PSS
воркеров сразу после fork) / (размер данных родителя)`. Baseline даёт
около 1 (почти полная копия на каждого воркера), точное значение
фиксируется при реализации.

→ **Боль №1: N воркеров = N копий данных.**

### 2. Почему RSS не падает после `del` (фундамент)

- pymalloc: арены и пулы (в 3.10+ арена 1 МиБ, пул 16 КиБ; проверить на версии
  runner). Арена возвращается ОС, только когда в ней не осталось ни одного живого
  объекта.
- `viz id=pymalloc-arenas`: удаление объектов «через один» не освобождает ни одной
  арены.
- `experiment`: создать ~1M мелких объектов, удалить 90% вразброс, сравнить
  `tracemalloc` (что думает Python) и RSS (что видит ОС).
- Вывод для практики: «утечка» в долгоживущем сервисе часто оказывается
  фрагментацией. `--max-requests` у gunicorn лечит симптом, а не причину.

Задания нет.

### 3. GIL: что он на самом деле запрещает

- `experiment`: 1 и 4 потока на трёх нагрузках. Чистый Python-цикл не
  ускоряется; `numpy.matmul` и инференс torch ускоряются, потому что отпускают GIL.
- `experiment`: oversubscription. 4 процесса × intra-op потоки torch по умолчанию
  (= все ядра) дают throughput хуже, чем 1 процесс.

**Задание 2 (Python)**: подобрать `workers × torch.set_num_threads` для
фиксированного объёма работы (K инференсов маленькой модели) при числе ядер
машины. `target: speedup >= 1.5` против наивной конфигурации (4 процесса,
потоки по умолчанию). Студент правит функцию, возвращающую конфигурацию, а
harness запускает пул и меряет время.

Если ядер меньше 4, harness возвращает понятное сообщение
(«на машине N ядер, задание требует ≥ 4»), а не проваленный вердикт.

→ **Боль №2: параллелизм в Python настраивается руками, и его легко сделать хуже.**

### 4. Event loop и синхронная модель

Без HTTP, чтобы не зависеть от подпроекта 2:

- `experiment`: asyncio-цикл, задача-«пульс» меряет лаг цикла каждые 10 мс,
  «эндпоинт» вызывает синхронный `model(x)` внутри `async def`. Лаг вырастает до
  длительности инференса, а «`/health`» ждёт вместе со всеми.
- Исправления: `asyncio.to_thread` / `run_in_executor`; обычный `def` в FastAPI,
  который фреймворк сам отправляет в threadpool.
- Связь с п. 3: в потоке это работает, потому что torch отпускает GIL.

→ **Боль №3: один `async def` блокирует весь сервис.**

### 5. Сериализация и копии на границе

- Запрос на изображение 224×224×3. Сравниваем JSON-список float → `torch.tensor(list)`
  с бинарным телом → `np.frombuffer` → `torch.from_numpy` (ноль копий).
- Таблица: сколько копий данных и сколько времени на каждом пути.

**Задание 3 (Python)**: ускорить декодирование payload в тензор.
`target: speedup >= 5`. Корректность: тензор совпадает с эталонным
(форма, dtype, значения).

→ **Боль №4: на текстовом протоколе время уходит на копирование и парсинг,
а не на модель.**

### 6. Вывод и мост

Четыре боли сводятся в таблицу. Следующий раздел собирает наивный сервис
FastAPI + torch и получает их все сразу, плюс пятую: модель обрабатывает
запросы по одному, без батчинга. Triton закрывает их устройством: C++ сервер
без GIL, одна копия модели на инстанс, бинарный протокол и shared memory,
dynamic batching.

## 5. Доработки платформы

### 5.1. torch в runner

- `torch` CPU-only: на x86 из индекса `https://download.pytorch.org/whl/cpu`,
  на arm64 из PyPI. Ожидаемый прирост образа ~200–250 МБ; torchvision не нужен.
- Модели создаются в коде harness'а со случайными весами (маленький CNN/MLP).
  Runner не имеет выхода в интернет, а для замеров производительности
  значения весов не важны.

### 5.2. Лимит памяти

`RLIMIT_AS` ограничивает виртуальную память. torch и OpenBLAS резервируют
адресное пространство с большим запасом, и под лимитом 2 ГиБ `import torch`,
вероятно, падает.

- Новое поле `meta.yml`: `memory_limit: as | none`, по умолчанию `as`
  (поведение первой части не меняется).
- Для `none` реальной границей служит лимит памяти контейнера: в
  `docker-compose.yml` у `runner` добавляется `mem_limit` (значение
  согласовать с README: «в Docker должно быть доступно хотя бы 4 ГиБ»).
- **Первая задача реализации — спайк**: подтвердить падение torch под
  `RLIMIT_AS` и найти минимальное рабочее значение. Если torch работает при
  разумном лимите, поле `memory_limit` не вводится, а harness'ам просто
  поднимается `memory_mb`.

### 5.3. Число потоков

Сейчас `_prepare_python` всегда выставляет `OMP_NUM_THREADS=1`. Новое поле
`meta.yml`: `threads: 1 | auto`, по умолчанию `1`. При `auto` переменная не
выставляется, потоками управляет harness / код студента.

### 5.4. Произвольные метрики и направление сравнения

- `bench.py` может вернуть `"metrics": {"<имя>": <число>, ...}` рядом с
  `samples`.
- Синтаксис `target` в блоке `exercise`: `<метрика> (>=|<=) <число>`.
  `speedup` остаётся встроенной метрикой, вычисляемой runner'ом, и
  `target: speedup >= 3` работает как раньше.
- Вердикт: `passed = correct AND сравнение(метрика, порог)`.
- Метрика, указанная в `target` и не возвращённая harness'ом, приводит к
  ошибке harness'а с понятным сообщением, а не к молчаливому провалу.
- В ответе `/api/run` появляется поле `metrics`. UI показывает целевую метрику
  вместо `speedup`, если она отличается.

### 5.5. Измерение PSS

Вспомогательный модуль для harness'ов (внутри `content/20-python-runtime/harness/_lib/`
или копируемый runner'ом рядом с `bench.py`). Он читает `Pss:` из
`/proc/<pid>/smaps_rollup` дочерних процессов. Работает и в Docker Desktop
на macOS, потому что контейнеры там исполняются в Linux VM.

### 5.6. Графики-серии

Новый тип harness'а `kind: series`: одна реализация, без A/B и вердикта, на
выходе несколько именованных линий. Последняя строка вывода `bench.py`:

```json
{ "lines": [ { "name": "worker 1", "points": [ {"x": 0.0, "y": 312.5} ] } ] }
```

Ответ `/api/run` содержит `lines` (ключ `series` уже занят sweep'ом, его
формат `{size, ms_per_element}` и график лестницы кэша не меняются). Подписи
осей задаются параметрами блока (`x_label`, `y_label`), как у существующего
sweep. Блок объявляется так же, как sweep (`benchmark` с `source:`).

### 5.7. Новые viz

- `web/static/viz/cow-pages.js`: страницы родителя/ребёнка, копирование
  при записи refcount;
- `web/static/viz/pymalloc-arenas.js`: арены/пулы, фрагментация после удаления.

Оба модуля экспортируют `mount(element, params)`, как и существующие.

## 6. Тестирование

Реализация по TDD, конвенции первой части сохраняются.

**Unit (общий прогон):**

- парсер `target`: `speedup >= 3`, `pss_growth_ratio <= 0.3`; ошибки на
  неизвестный оператор и мусор;
- `meta.yml`: поля `memory_limit`, `threads`, их значения по умолчанию;
- вердикт по произвольной метрике в обоих направлениях; отсутствующая метрика
  даёт ошибку harness'а;
- `_prepare_python`: при `threads: auto` переменная `OMP_NUM_THREADS` не
  выставляется;
- `kind: series`: разбор вывода, ошибки на пустых линиях и точках без x/y;
  sweep-ответ не меняется.

**`make verify-content` (на целевой машине):**

- для каждого из трёх заданий эталон проходит порог, а стартовый код нет;
- задание 2 на машине с < 4 ядрами возвращает сообщение о нехватке ядер;
- крючок воспроизводимо показывает рост PSS > 2× размера данных суммарно
  по воркерам.

**Smoke:** раздел рендерится, `import torch` в runner проходит, `/api/run` на
каждом новом harness'е возвращает валидный ответ.
