## 2. Кэш и порядок обхода

### Порядок обращений к памяти

CPU работает с ограниченной скоростью. Каждая операция (сложение, умножение, переход в ветку программы, ...) выполняется за некоторое число *тактов* на ядро.
Например, сложение 2 чисел может занимать 1 *такт*, деление — 12 *такта* (упрощенно).
Современные процессоры работают на частотах 3–6 ГГц, то есть 3 000 000 000–6 000 000 000 *тактов* в секунду.

Рассмотрим наш пример суммирования матрицы:
- Матрица `4 × 4`: 16 чтений и 16 сложений в каждом варианте.
- Удерживайте «Такт» или Enter. Следите за тактами ожидания памяти.

```viz id=traversal-walk
size: 4
```

Примерно так можно представить работу CPU наивным образом.
В этой модели у нас присутствует только память и сам процессор. Мы видим, что принципиальных различий в работе кода нет вообще.
Почему же тогда в реальном примере замеры так сильно отличаются?

### cache

Скорость работы CPU уже давно нельзя измерять просто *тактами*.
Частота работы (ГГц) за последние десятилетия почти не менялась. В начале нулевых инженеры просто уперлись в законы физики.

Однако CPU продолжают ускоряться. Ускорение происходит из-за целого ряда хитрых оптимизаций, одна из самых главных — *кэш*.

Современные CPU имеют несколько быстрых блоков памяти, встроенных прямо в чип процессора.
У Intel их 3 — L1 Cache, L2 Cache, L3 Cache.

Когда программе нужно получить доступ к «переменной», CPU сначала идет в RAM, прихранивает значение в кэше и при следующем запросе этой переменной берет ее из кэша.

Если CPU необходимо взять какое-то значение (например, для сложения) и его нет в кэше, мы говорим, что произошел *промах* (cache-miss).
Если значение есть в кэше — это *попадание* (cache-hit).

Пример иерархии доступа к памяти: Intel Xeon Platinum 8480+, DDR5-4800. Задержки на графике ориентировочные.

```viz id=memory-latency
```
[Характеристики Intel](https://www.intel.com/content/www/us/en/products/sku/231746/intel-xeon-platinum-8480-processor-105m-cache-2-00-ghz/specifications.html) · [Замеры задержек](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids) · [Кэши других CPU](https://hw-museum.cz/cpu/cpu-interactive-table).

Главное тут: RAM очень медленный по сравнению с памятью на чипе. В прошлой демонстрации можно увидеть, что без кэша CPU просто работает вхолостую большую часть времени, так как мы ждем, пока данные придут из памяти.

Последнее, о чем тут важно сказать: CPU никогда не вытягивает из памяти одно конкретное значение. Всегда вытягивается сразу несколько рядом стоящих значений, и все они записываются в кэш. Такой блок рядом стоящих данных называется *кэш-линией*. Обычно он занимает 64 байта.
То есть, если программе нужно получить значение int64, процессор вытянет область памяти по нужному адресу И еще несколько значений рядом.

- Кэш модели вмещает одну линию: 64 байта, 16 соседних `int`.
- Общий такт для двух колонок. Сравните попадания, загрузки и время завершения.

## 3. Prefetcher

Мы увидели, что порядок, в котором мы стучимся к памяти, имеет огромное значение.
Гораздо выгоднее проходить ее последовательно. Однако если мы снова посмотрим на предыдущую демонстрацию *(ДВА ПОРЯДКА ОБХОДА
8 × 8 · INT)*, мы увидим, что даже в быстром варианте процессор все равно периодически простаивает, когда он выходит за пределы кэш-линии.

Поскольку прямой обход памяти — это очень частое и естественное действие, процессор спекулятивно подтягивает сразу несколько кэш-линий из памяти. Это происходит в отдельном блоке CPU и работает параллельно с основной программой.

Называется это *Prefetching*.

```viz id=prefetch-lines
```

- Мы видим, что в таким механизмом CPU не простаивает вообще.
- Глубина предвыборки зависит от CPU. Прогноз может ошибаться; соседние линии загружаются не при каждом запросе.

### Последовательный и перемешанный порядок

## 5. Параллельное выполнение

В большинстве программ, кроме простого обхода, есть еще множество ветвлений if, switch, goto.
Программа — это та же самая память. И

Инструкции (сложение, деление, ...) тоже зачитываются из памяти и кэшируются.
Обычно L1I хранит инструкции, L1D — данные.

Рассмотрим простую программу:
``` asm
ADD EAX, 1 ; +1 к регистру A
SUB EBX, 2 ; -2 к регистру B
```

Мы не будем рассматривать ассемблер в данном курсе. Я надеюсь, что этот пример достаточно простой, чтобы понять, что происходит.

ADD, SUB — операции.
EAX, EBX — регистры (если совсем упрощенно, можно рассматривать их как переменные).

Пример выше эквивалентен:
```
x = x + 1
y = y - 2
```

Простая модель выполнения программы:
1. CPU загружает эти инструкции из памяти и кладет в кэш;
2. CPU выполняет первую инструкцию;
3. CPU выполняет вторую инструкцию.

В этой последовательной модели время выполнения равно T(OP1) + T(OP2).

```viz id=execution-blocks
```

В CPU есть множество отдельных блоков для вычислений. Несколько сложений, несколько вычитаний и т. д.
Они не зависят друг от друга. Один такт может запустить сразу несколько блоков. Но в упрощенной модели
мы запускаем ADD и SUB последовательно.

В теории можно рассматривать блоки ADD, SUB, ... как отдельные микроядра и запускать их параллельно.

Современные CPU могут выполнять независимые операции параллельно на разных блоках.

```viz id=execution-parallel
```

Итак, мы узнали, что CPU может распараллеливать работу даже в пределах одного ядра.
Из этого следует, что процессор в общем случае может выполнять операции быстрее тактовой частоты.

Как это влияет на техники оптимизации? Разберемся в следующем разделе.

> Как вы думаете, может ли CPU распараллелить `ADD EAX; SUB EAX`?

- В обоих циклах четыре сложения за итерацию и одинаковый порядок чтения. Один поток, массив из 4096 чисел `double` занимает 32 КиБ и многократно используется повторно.

### SIMD

Single instruction, multiple data (SIMD) — это набор инструкций для обработки батчей данных вместо отдельных переменных.

Вместо
```
ADD EAX, EBX
```
можно выполнять батчевую инструкцию:
```
ADDPS [array1], [array2]
```

Это по факту явный способ распараллелить вычисления на одном ядре.

- Задача: `out[i] = a[i] + b[i]`.
- Слева — одна пара за операцию, справа — четыре пары.
- Шаг показывает операцию сложения, а не такт реального CPU.

```viz id=simd-add
```

SIMD часто встречается в низкоуровневых оптимизациях, при этом иногда в неожиданных местах.
Хороший пример — это [simdjson](https://github.com/simdjson/simdjson).
Гипероптимизированная библиотека для парсинга JSON.
Кроме SIMD, там применяются и много других оптимизаций, например, из парсера практически убраны «if».
Есть интересное [видео с докладом](https://www.youtube.com/watch?v=wlvKAT7SZIQ), где рассказывается, как этого удалось достичь.

## 6. Пайплайнинг и выполнение вне очереди

Последний механизм CPU, который мы сегодня обсудим, — это пайплайнинг (конвейер).
Для того чтобы просто сложить 2 числа, нужно:
1. вытащить их из RAM;
2. выполнить `ADD`;
3. записать результат в RAM.

Мы уже рассматривали, что вытягивание из RAM может работать параллельно выполнению. В реальности CPU запускает внутри себя конвейерную обработку. Если в CPU свободен какой-либо блок, он может подтянуть операции из очереди и начать выполнять их. Более того, если CPU посчитает нужным, он может поменять порядок операций, если видит, что нужный блок выполнения свободен в данный момент.
Например:
```
ADD EAX, 1
ADD ECX, 3
SUB EBX, 2
```

`SUB` может выполниться перед ADD, если блок SUB свободен. Хотя программист указал вполне определенный порядок.
Таким образом достигается максимально эффективная утилизация CPU.

```viz id=cpu-overlap
```

### Амортизация вызовов Python

Поскольку мы из питона запускаем код на другом языке, появляются накладные расходы (копирование строк, каст типов, ...). Это вносит заметные задержки и иногда может быть дольше самого вызова Си-функции.

Тут показывается техника для минимизации такого рода задержек. Основная идея — батчировать данные и делать один вызов Си-функции сразу для нескольких запросов.

На входе — поток обычных словарей Python, как после разбора JSON: `{"id": 101, "score": -0.2}`. Нужно ограничить оценки диапазоном `[0, 1]` и вернуть список в исходном порядке.

- При `BATCH_SIZE = 1` каждая запись отдельно преобразуется в массив и обрабатывается NumPy.
- Увеличьте `BATCH_SIZE`, чтобы собирать записи в пакет и обрабатывать его одним вызовом `np.clip`.
- `batched` берёт записи из итератора порциями. Последний пакет может быть неполным. Пример использует Python 3.12 или новее.

```benchmark id=numpy-batch lang=python
harness: numpy_batch
variants: [single, batch]
starter: snippets/numpy_batch_single.py
history_parameter: BATCH_SIZE
title: Сбор записей в пакеты перед вызовом NumPy
```

Замер включает сбор пакетов, извлечение чисел из словарей, создание массивов NumPy, вычисление и преобразование результата обратно в список Python. На входе 65 539 записей; их создание и проверка результата не входят в замер.

## 9. Компиляция Python-кода с Numba

Есть случаи, когда готовых Си-библиотек нет. Тогда может возникнуть идея написать отдельный сервис, например на Go, и реализовать алгоритм в нем.

Тут я хочу показать, что в питоне есть готовые инструменты для быстрого написание оптимизированного кода.
Один из них — Numba. Это библиотека для JIT (Just In Time) компиляции подмножества питона.
Numba компилирует функцию на Python прямо во время работы программы. Она делает это за счет сбора статистики выполнения функции.
В результате наш код на питоне превращается в настоящие инструкции процессора, так, будто мы написали его на Си.

- `@njit` компилирует поддерживаемый численный код в машинный.

### Несколько операций за один проход

- 524 288 значений `int64`: ограничить `[−200, 200]` до `[−100, 100]`, сложить квадраты.
- NumPy создаёт промежуточные массивы; Numba объединяет вычисления в одном цикле.

```benchmark id=numba-energy lang=python
harness: numba_energy
variants: [numpy, numba]
parallel_editors: true
layout: stacked
title: Промежуточные массивы и один проход
labels: ["NumPy", "Цикл с @njit"]
```

Numba в этом случае даже быстрее NumPy.

### Faiss vs Numba

Faiss — библиотека, предоставляющая набор алгоритмов и структур данных для быстрого поиска по N-мерным векторам. Чаще всего она используется для семантического поиска.

- Есть 262 144 точки на плоскости, каждая — пара координат `(x, y)` в `float32`. Для 64 запросов нужно вернуть индексы ближайших точек.
- Faiss использует `IndexFlatL2(2)` — точный полный перебор. Numba тоже проверяет все точки, но код написан специально для двух координат и одного ближайшего соседа.
- Обе реализации работают в один поток. Построение индекса Faiss, компиляция Numba, прогрев и проверка не входят в замер. Измеряется поиск для всех 64 запросов.

```benchmark id=faiss-numba lang=python
harness: faiss_numba
variants: [faiss, numba]
parallel_editors: true
layout: stacked
title: Ближайшая точка на плоскости
labels: ["Faiss · IndexFlatL2", "Numba · цикл для двух координат"]
```

Иногда, выбрав правильный инструмент, можно обогнать даже оптимизированные библиотеки.

## 10. Заключение

Мы рассмотрели много всего. Основная идея, которую я хочу донести:
Современные CPU очень быстрые даже на одном ядре.

Мы увидели, например, что чтение из памяти и работа с данными эффективно параллелятся. Часто обращения к памяти можно минимизировать.
Это значит, что для простых алгоритмов можно обрабатывать данные фактически со скоростью памяти.

Даже для сложных алгоритмов CPU выполняет миллиарды операций на одной ядре, еще и параллелит их.
Именно от этого можно отталкиваться при оценке: работает ли алгоритм быстро или медленно.
Часто алгоритмы можно ускорять на порядки, используя батчинг и подобрав правильный формат данных. Не нужно для этого добавлять сотни подов.

В качестве небольшого упражнения я предлагаю вам посмотреть скорость работы RAM на вашем компьютере.
Зная эту скорость, можете ли вы прикинуть, сколько времени займет обработка 50GB метрик? Допустим, у нас есть в памяти файл с 50GB данным о срабатывание правила в детекторе, и нужно сказать, сколько всего было срабатываний в файле?

Можно ли предположить, что это можно посчитать быстрее, чем за 1 секунду?
