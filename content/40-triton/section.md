Прошлая часть закончилась списком. Руками мы вынесли модель в поток, перешли на бинарный протокол, подобрали потоки и воркеры, написали очередь со сбором батча и подобрали `max_batch_size` и `max_queue_delay`. Многое сделать не успели: ошибка одного входа валит весь батч, очередь не ограничена, модель одна и в одной версии, метрик нет. И один вопрос остался открытым: на одном экземпляре модели ожидание в очереди не окупилось.

Triton Inference Server обещает почти всё это конфигурацией модели. В этой части мы не будем верить обещаниям на слово. Поставим ту же `widemodel` в Triton, подадим ту же нагрузку тем же генератором на тех же трёх CPU и замерами проверим, что он снимает, что снимает частично и что по-прежнему приходится настраивать руками.

## 0. Крючок: Triton не магия

Начнём с минимального конфига. Модель работает в python backend: Triton запускает наш `model.py`, в котором тот же torch-код, что в сервисе из прошлой части. Батчи до 32 элементов разрешены (`max_batch_size: 32`), экземпляр модели один, у `torch` три потока — как у сервиса из подглавы 4 прошлой части.

Стенд:

- Triton — отдельный контейнер курса, прибитый к трём CPU (переменная `TRITON_CPUS`, по умолчанию 1–3). Харнесс кладёт конфиг блока в репозиторий моделей, загружает модель через HTTP API сервера и после замера выгружает;
- генератор нагрузки тот же, что в прошлой части: открытый цикл на CPU 0, latency от запланированного момента отправки;
- запросы — протокол KServe v2, по одному изображению 3×64×64 в бинарном виде (о протоколе — в подглаве 1);
- сначала харнесс меряет ёмкость Triton C, затем подаёт ступени 0,25 C … 1,25 C по две секунды;
- на тех же ступенях и тех же CPU харнесс поднимает сервис из прошлой части с батчем из одного: стартовый код задания из подглавы 4, бинарный протокол, `widemodel`;
- средний батч Triton берётся из его метрик: сколько элементов модель обработала, делённое на число её запусков.

Конфиг можно править прямо в блоке: замер возьмёт вашу версию.

```benchmark id=triton-hook lang=pbtxt
harness: hook
source: snippets/config_minimal.pbtxt
starter: snippets/config_minimal.pbtxt
x_label: запросов в секунду
y_label: мс (p50, p99) и штук (батч)
title: Triton без настройки против батча из одного
log_y: true
```

В нашем замере ёмкость Triton — около 400 ответов в секунду. Пока нагрузка ниже ёмкости, p99 и у Triton, и у сервиса из прошлой части 3–4 мс. Выше ёмкости оба отвечают примерно 415 раз в секунду, очередь растёт у обоих одинаково, и при 1,25 C p99 у обоих около 400 мс. Средний батч Triton на всех ступенях — 1,00, хотя `max_batch_size: 32` разрешает больше.

Triton не склеивает запросы сам. `max_batch_size` говорит только, что модель умеет принимать батч, а собирать батчи из отдельных запросов — отдельный механизм, `dynamic_batching`, и без него в конфиге запросы исполняются по одному. Дальше мы будем включать механизмы Triton по одному и мерить каждый.

## 1. Репозиторий моделей, конфиг и протокол

Triton берёт модели из репозитория — каталога, где каждой модели соответствует подкаталог:

```text
models/
  widemodel/
    config.pbtxt      # конфиг модели
    1/                # версия 1
      model.py        # для python backend; для libtorch — model.pt
      widemodel.py
```

`config.pbtxt` — текстовый формат protobuf. В минимальном конфиге из крючка:

- `backend: "python"` — модель исполняет python backend: отдельный процесс-заглушка на каждый экземпляр модели, в котором работает наш `model.py`. Triton передаёт ему входы через общую память, а `model.py` возвращает ответы;
- `max_batch_size: 32` — модель принимает батч до 32 элементов. Размер батча не входит в `dims`: Triton добавляет его первым измерением сам;
- `input` и `output` — имена, типы и формы тензоров без измерения батча. Вход — `INPUT__0`, `float32` 3×64×64, выход — `OUTPUT__0`, 10 чисел;
- `instance_group` — сколько экземпляров модели держать и где: `count: 1`, `kind: KIND_CPU`;
- `parameters` — произвольные пары ключ–значение, которые получает `model.py`. Наш читает `TORCH_THREADS` и зовёт `torch.set_num_threads`.

Клиенты говорят с Triton по протоколу KServe v2: `POST /v2/models/<имя>/infer`, тело — JSON со списком входов. Тензор можно передать прямо в JSON, списком из 12 288 чисел. Или воспользоваться binary extension: в JSON остаются только имя, форма и тип входа, а сами числа идут следом сырыми байтами `float32`. Длину JSON-части клиент передаёт в заголовке `Inference-Header-Content-Length`. Это тот же переход, что в подглаве 1 прошлой части, только описанный стандартным протоколом, а не нашей договорённостью.

Сравним оба варианта на одной модели. Сначала харнесс меряет ёмкость с каждым видом тела, затем подаёт одинаковые ступени 0,25–0,9 от ёмкости бинарного варианта.

```benchmark id=triton-protocol lang=pbtxt
harness: protocol
source: snippets/config_minimal.pbtxt
x_label: запросов в секунду
y_label: p99, мс
title: KServe v2 — JSON против binary extension
```

В нашем замере JSON-тело весит 248 КиБ (числа `float32` с полной точностью), бинарное — 48 КиБ. JSON стоит около миллисекунды на запрос: p50 при 100 RPS — 4,4 мс против 3,6 мс у бинарного тела, на остальных ступенях разница 0,7–1,7 мс. А вот ёмкость почти не меняется: 398 ответов в секунду с JSON против 409 с бинарным телом.

В прошлой части текстовый протокол бил и по задержке, и по ёмкости: JSON разбирал тот же процесс Python, который считал модель. У Triton тело разбирает его HTTP-сервер, а не поток, в котором работает модель, поэтому в нашем замере узким местом осталась модель, а протокол добавил только задержку. Дальше в части все замеры идут с binary extension.

## 2. `dynamic_batching` против своего батчера

В прошлой части мы написали батчер сами: очередь, `asyncio.Future` на каждый запрос, сбор батча с дедлайном и раздачу строк выхода. У Triton то же самое включается одной секцией конфига:

```text
dynamic_batching {
  max_queue_delay_microseconds: 0     # сколько первый запрос ждёт попутчиков
  preferred_batch_size: [ 8, 16 ]     # размеры, на которых можно не ждать дальше
}
```

Все поля необязательны, и пустая секция `dynamic_batching { }` тоже включает батчинг. Поля значат следующее:

- `max_queue_delay_microseconds` — тот же `max_queue_delay`, что в нашем батчере, только в микросекундах. По умолчанию 0: Triton не ждёт попутчиков специально, а забирает в батч всё, что уже стоит в очереди, пока модель занята предыдущим батчем. Именно такой режим в подглаве 5 прошлой части оказался не хуже ожидания;
- `preferred_batch_size` — размеры батча, при которых планировщик отправляет батч сразу, не дожидаясь `max_queue_delay`. Без этого поля он старается набрать `max_batch_size`;
- верхняя граница батча — `max_batch_size` модели, отдельно её задавать не нужно.

Ответы раздаёт сам Triton: каждый запрос получает свою часть выхода. Наш `model.py` получает список запросов, склеивает их входы в один тензор и режет выход обратно. В python backend эту склейку пишет автор `model.py`, а backend для libtorch делает её сам (подглава 4).

Нагрузка задания — та же, что в задании прошлой части: 700 запросов в секунду по две секунды, SLO 50 мс. Порог — goodput хотя бы вдвое выше, чем у стартового конфига. Перед замером харнесс сверяет конфиг так, как его понял сервер: батч разрешён, вход `INPUT__0` и выход `OUTPUT__0` нужных форм. Если Triton не смог разобрать конфиг, вы увидите его сообщение с номером строки. Поле `name` писать не нужно: имя модели харнесс задаёт сам. Затем пять редких запросов с интервалом 300 мс: слишком большой `max_queue_delay_microseconds` заставит одиночный запрос ждать попутчиков, которых нет, и харнесс скажет об этом прямо.

Теперь сравним Triton со своим батчером из прошлой части на одинаковых ступенях нагрузки. Батчер — эталон задания прошлой части: батч до 32, ожидание до 5 мс, три потока `torch`, те же три CPU. В блоке ниже исходно стоит стартовый конфиг без батчинга. Вставьте в него свой конфиг из задания и запустите замер.

```benchmark id=triton-batching lang=pbtxt

starter: snippets/config_starter.pbtxt
x_label: запросов в секунду
y_label: мс (p99) и штук (батч)

```

В нашем замере с `dynamic_batching { }` Triton держит все ступени до 1100 запросов в секунду, p99 15–24 мс. Средний батч растёт вместе с нагрузкой: 1,0 при 100–300 RPS, около 4 при 700, 6,6 при 1100. Свой батчер тоже держит все ступени, p99 20–30 мс на 300 RPS и выше. Заметная разница — при малой нагрузке: при 100 RPS p50 у Triton 3,9 мс против 8,6 мс у своего батчера. Это не заслуга C++: наш батчер ждёт попутчиков до 5 мс, а Triton по умолчанию не ждёт вовсе. Без конфига батчинга на тех же ступенях всё ломается уже после 400 RPS — это видно, если запустить блок со стартовым конфигом.

Итог подглавы: dynamic batching Triton закрывает ту же боль №5, что наш батчер, и на нашей модели не хуже него. Писать очередь, future и раздачу ответов больше не нужно. Склейку входов в python backend по-прежнему пишет автор `model.py`, а выбирать задержку по-прежнему приходится замером.

## 3. Несколько экземпляров и ожидание в очереди

В подглаве 5 прошлой части ожидание в очереди не окупилось: при одном экземпляре модели запросы и так копятся, пока модель считает предыдущий батч, и ждать попутчиков специально незачем. Мы предположили, что ожидание окупится, когда экземпляров модели несколько. Теперь это можно проверить: число экземпляров в Triton — одна строка конфига.

```text
instance_group [ { count: 3 kind: KIND_CPU } ]
```

Каждый экземпляр — отдельная копия модели: в python backend — отдельный процесс со своим `model.py`. Планировщик dynamic batching отдаёт собранный батч первому свободному экземпляру. Экземпляры делят те же три CPU, поэтому потоки `torch` харнесс делит между ними: 1 экземпляр × 3 потока, 2 × 1, 3 × 1. Вместе — не больше трёх потоков на три CPU. Сколько потоков дать экземпляру, Triton не решает: это наш параметр `TORCH_THREADS` в конфиге.

Сетка замера: 1, 2 и 3 экземпляра, `max_queue_delay_microseconds` 0, 2, 5 и 10 мс, нагрузка 100 и 700 запросов в секунду по две секунды. Отдельная линия — переподписка: 3 экземпляра по 3 потока, то есть 9 потоков на три CPU. Замер идёт несколько минут: на каждую точку сетки харнесс заново загружает модель.

```benchmark id=triton-instances lang=pbtxt
harness: instances_delay
source: snippets/config_ref.pbtxt
x_label: max_queue_delay, мс
y_label: мс
title: Экземпляры модели × ожидание в очереди
log_y: true
```

В нашем замере (три прогона, цифры повторялись с точностью до миллисекунды-двух):

- при 100 RPS ожидание стоит ровно столько, сколько ждёт запрос: p50 3,5–3,9 мс без ожидания, 8,6 мс при 5 мс, 13,7 мс при 10 мс — при любом числе экземпляров. Батч при этом почти не растёт: попутчиков мало;
- при 700 RPS и одном экземпляре ожидание не помогает, как и в прошлой части: p99 13–18 мс без ожидания и 15–20 мс с ним;
- при 700 RPS и нескольких экземплярах ожидание окупается. Без него свободный экземпляр сразу забирает то, что есть, и батчи мельче — 2–3 запроса по метрикам Triton, а мелкий батч у `widemodel` дорог: веса читаются ради нескольких элементов (подглава 2 прошлой части). С ожиданием 5 мс батч дорастает до 4, и p99 падает с 19 до 14 мс при двух экземплярах и с 26–27 до 14 мс при трёх. При 10 мс снова хуже — около 20 мс: теперь лишнее ожидание дороже, чем выигрыш от батча;
- переподписка — 9 потоков на 3 CPU — даёт p99 больше 100 мс без ожидания и 85–120 мс при 5 мс. При 10 мс батчи крупнее и p99 падает, но от прогона к прогону скачет от 20 до 51 мс. Девять потоков на трёх ядрах вытесняют друг друга, и замер становится нестабильным.

Гипотеза прошлой части подтвердилась: при нескольких экземплярах ожидание в очереди окупается, и у него есть оптимум. Но выиграли мы немного. Лучший результат с несколькими экземплярами — около 14 мс — лишь догоняет один экземпляр с тремя потоками без ожидания. В нашем замере `torch` и одним вызовом модели занимает все три ядра. Окупятся ли несколько экземпляров сильнее на другом железе или с другой моделью, этот замер не говорит — это проверяется таким же замером там.

Что Triton здесь сделал за нас: раздал батчи по экземплярам и поднял процессы под них. Что осталось руками: число экземпляров, потоки на экземпляр так, чтобы вместе не переподписать CPU, и задержку — всё это мы подобрали замером, как и в прошлой части.

## 4. Без Python: libtorch backend

До сих пор модель исполнял python backend: на каждый экземпляр — процесс с интерпретатором Python, наш `model.py`, склейка входов батча и раздача выходов, написанные нами. У Triton есть backend, которому Python не нужен вовсе: `pytorch_libtorch` исполняет TorchScript — сохранённое в файл представление модели, которое умеет загружать C++-библиотека `libtorch`. Модель экспортируется один раз, а дальше в репозитории лежит только файл `1/model.pt` и конфиг:

```text
platform: "pytorch_libtorch"
max_batch_size: 32
input [ { name: "INPUT__0" data_type: TYPE_FP32 dims: [ 3, 64, 64 ] } ]
output [ { name: "OUTPUT__0" data_type: TYPE_FP32 dims: [ 10 ] } ]
```

Что меняется по сравнению с python backend:

- склеивать входы батча и резать выход больше не нужно: backend делает это сам;
- имена `INPUT__0` и `OUTPUT__0` — соглашение backend: по номеру после двух подчёркиваний он сопоставляет тензоры с аргументами и выходами модели;
- потоки задаёт параметр backend `INTRA_OP_THREAD_COUNT` вместо нашего `TORCH_THREADS`;
- экспорт — ручной шаг. `torch.jit.trace` прогоняет модель на примере входа и записывает операции, которые выполнились. Всё, что зависело от конкретного примера — ветки `if` по данным, размеры, превращённые в числа Python, — записывается как константа.

В `torch` 2.15 `torch.jit.trace` работает, но печатает предупреждение: TorchScript объявлен устаревшим, и `torch` предлагает переходить на `torch.compile` и `torch.export`. Для `pytorch_libtorch` нужен именно TorchScript, поэтому в этой подглаве мы им пользуемся, а предупреждение в выводе — ожидаемое.

```exercise id=export-exercise lang=python
title: Перенести модель в libtorch
target: goodput_ratio >= 0.9
starter: snippets/export_starter.py
reference: snippets/export_ref.py
harness: export_exercise
```

Харнесс вызывает вашу `export` с моделью `widemodel`, кладёт файл в репозиторий и загружает его с вашим `CONFIG`. Затем шлёт три запроса с батчами 1, 7 и 32 и сверяет ответы с исходной моделью: модель, в которую при экспорте «зашился» размер батча, ответит на первый и сломается на втором — харнесс скажет об этом прямо. После этого — нагрузка 1100 запросов в секунду, SLO 50 мс, по три прогона. Точка сравнения — python backend с dynamic batching из подглавы 2. Порог — не хуже него: goodput хотя бы 0,9 от python backend.

Порог «не хуже», а не «быстрее», выбран по замеру. Сравним оба backend на одинаковом батчинге:

```benchmark id=triton-libtorch lang=pbtxt
harness: libtorch
source: snippets/config_libtorch.pbtxt
x_label: запросов в секунду
y_label: мс
title: python backend против libtorch
```

В нашем замере (три прогона) оба backend держат все ступени до 1500 запросов в секунду. Медиана у libtorch стабильно чуть ниже: 2,4 мс против 2,6 мс при 300 RPS, 7,4 против 8,0–8,2 мс при 1100 RPS, 8,2–8,3 против 9,7 мс при 1500 RPS. p99 скачет от прогона к прогону сильнее, чем различается между backend: 11–18 мс у обоих при 700–1100 RPS. Число потоков `INTRA_OP_THREAD_COUNT` — 1, 3 или значение по умолчанию — в нашем замере ничего не изменило.

Объяснение — то же, что в подглаве 2 прошлой части: `widemodel` упирается в чтение 112 МиБ весов из памяти, а не в Python и не в арифметику. Интерпретатор Python добавлял к каждому батчу немного накладных расходов, и libtorch убрал только их. Для модели, где Python-код вокруг вызова тяжелее — разбор входов, постобработка, мелкие операции в цикле, — разница может быть больше. Это проверяется таким же замером на своей модели.

Что дал переход: меньше нашего кода (никакого `model.py`), загрузка модели за доли секунды вместо трёх с половиной и около миллисекунды медианы под нагрузкой. Что потребовал: ручной экспорт с риском «зашить» в модель пример входа и формат, который сам `torch` уже объявил устаревшим.
